# User Story Map: ПСБ × ИТМО — анализ наполненности НБС

> **Итерация 1 — рабочая карта для обсуждения.** Обновлена по встрече 18.11.2026 и сверена с C4/ER 18.11.2026. Единственный сценарий MVP — анализ наполненности по НБС для действующих клиентов. Номера сценария в стенограмме расходятся (11 и 2), поэтому карта называет его по содержанию. Сотрудники развития НБС, бизнес и ДЗО остаются группами пользователей; отдельно заказчик назвал две прикладные роли: администратор (может править данные) и пользователь анализа. Для локального MVP отдельный вход не предусмотрен; точные права и способ демонстрации различий действий не определены.

> **Уточнение 20.11.2026:** рабочий результат EPIC-005 — подсказка менеджеру с фактами, ссылками и пробелами. Формальных продуктовых правил, согласно пересланной переписке, нет. Предиктивный NBO из исходного ТЗ остаётся неснятым расхождением, но не входит в рабочий baseline. Для MVP выбраны отдельный ресурс публичных организаций, локальный переключатель роли без защиты API и создание нового среза при исправлении данных.

## Backbone (Путь пользователя)

Загрузить и проверить данные → Выбрать НБС, период и фильтры → Посмотреть наполненность по клиентам и регионам → Изучить клиента и его продукты → Собрать факты и рассмотреть подсказку → Рассмотреть продуктовые связки → Сравнить два временных среза → Настроить состав экспорта → Экспортировать граф и отчёт

**Основание и трактовка:** заказчик подтвердил, что в проекте остаётся один сценарий предоставления информации по НБС. Данные дочерних и внучатых компаний и иерархия холдинга из него исключены. Загрузка Excel/CSV остаётся тестовым способом показать загрузку в граф. Сравнение периодов может выполняться на любом шаге.

**Решение пользователя:** экспорт — обязательный финальный шаг сценария.

## Release 1.0 (MVP)

### [EPIC-001] Подготовить данные для анализа

---
**[US-001][Администратор] Как администратор, я хочу загрузить файл с данными о клиентах и продуктах, чтобы подготовить данные для сценария анализа наполненности НБС.**
- [ ] Я могу начать демонстрационный сценарий с файлом Excel или CSV.
- [ ] В загруженных данных могут быть сведения о клиенте, продуктах, конкурентах, условиях конкурентов и заметки сотрудника.
- [ ] [💡 Предложение] Система показывает сопоставление распознанных столбцов с характеристиками объектов и связей, чтобы я мог проверить его до использования данных.
- [ ] До использования данных я вижу, какие сведения распознаны и к каким клиентам или объектам они отнесены.
- [ ] Я вижу записи, которые не удалось однозначно связать с клиентом, и могу отличить их от данных, вошедших в анализ.
- [ ] При ошибках данных фиксация среза блокируется целиком; после исправления файла я повторяю предпросмотр.
- Notes: Заказчик подтвердил загрузку Excel/CSV как тестовый сценарий и назвал администратора ролью, которая может редактировать данные. Клиентские строки для демонстрации полностью синтетические; объём файла ещё не задан.
---
**[SS-001][Система] Как система, я хочу проверять загруженные сведения на дубли, пропуски и некорректные идентификаторы и показывать пользователю найденные проблемы, чтобы не скрывать качество исходных данных.**
- [ ] Пользователь видит сообщения о дублях, пропущенных значениях и некорректных ИНН.
- [ ] Для реального юридического лица ИНН проверяется как 10-значный номер с контрольной суммой; 12-значное правило исходного ТЗ относится к физическому лицу и не применяется к выбранному сценарию. Синтетические ID `DEMO-*` не ищутся во внешних источниках.
- [ ] Пользователь может понять, какие записи затронуты проблемой.
- [ ] [💡 Предложение] Записи с ошибками не выдаются за достоверно связанные с клиентом без подтверждения.
- Notes: ТЗ называет связку ИНН + КПП + внутренний Client ID основными ключами; конкретное поведение при конфликте или неоднозначном совпадении ещё нужно уточнить. ТЗ требует сопоставления колонок и показа ошибок, но не задаёт точный пользовательский процесс проверки сопоставлений и обработки ошибочных строк — оба AC выше являются предложениями.
---
**[US-012][Администратор] Как администратор, я хочу редактировать данные, чтобы актуализировать содержимое для анализа.**
- [ ] Администратор может менять данные, используемые в анализе.
- [ ] Роль пользователя анализа не даёт права редактировать данные.
- [ ] В локальном демо переключатель роли скрывает действия редактирования в режиме анализа; это демонстрация интерфейса без аутентификации и серверной авторизации.
- [ ] Исправление записи в использованном срезе создаёт новый срез с ссылкой на исходный; старый остаётся доступным для сравнения и воспроизведения карточки.
- [ ] [💡 Предложение] Администратор может дополнить перечень НБС, если нужного продукта в нём нет.
- Notes: На встрече названы администратор, который может редактировать данные, и вторая роль пользователя. Заказчик уточнил, что перечень НБС неполный, его нужно дополнять, а при изменении витрины он ожидает автообновления. Для локального MVP отдельный вход не предусмотрен; способ демонстрации ролей без входа и точные права не детализированы. Аутентификацию для будущего использования внутри Банка согласовать отдельно с ИБ.

### [EPIC-002] Выбрать НБС, период и срез анализа

---
**[US-002][Пользователь анализа] Как пользователь анализа, я хочу выбрать НБС, период и интересующие меня срезы, чтобы рассматривать нужную часть клиентского портфеля.**
- [ ] Я могу выбрать конкретный НБС для анализа.
- [ ] Я могу выбрать период с точностью день, месяц или год.
- [ ] Я могу ограничить представление доступными фильтрами, включая регион и сегмент.
- [ ] Текущее состояние выбранных фильтров и периода понятно из представления.
- Notes: В ТЗ фильтры перечислены общим образом; окончательный набор не зафиксирован. Для демонстрации выбран НБС «Страхование → ДМС»; формальной матрицы применимости, по пересланной переписке, нет.

### [EPIC-003] Посмотреть наполненность НБС и её распределение

---
**[US-003][Пользователь анализа] Как пользователь анализа, я хочу видеть, какие действующие клиенты используют выбранный НБС и где продукт распространён сильнее или слабее, чтобы находить точки роста.**
- [ ] Представление различает клиентов с выбранным продуктом и без него.
- [ ] Я могу увидеть распределение подключений по выбранным регионам и другим применённым срезам.
- [ ] Представление помогает обнаружить регионы и региональные центры с высокой наполненностью и те, где подключений мало или нет.
- [ ] Связи и показатели соответствуют выбранным данным и периоду.
- [ ] Обозначения и индикаторы понятны пользователю; структуру схемы можно понять примерно за 10–15 секунд.
- [ ] Продуктовая команда подтверждает, что такое представление удобнее таблицы для принятия решений.
- Notes: Сценарий не включает структуру владения. Отсутствие продукта само по себе не трактуется как возможность продажи; факты и пробелы собираются отдельно в EPIC-005.
---

### [EPIC-004] Изучить клиента и его продуктовый контекст

---
**[US-004][Пользователь анализа] Как пользователь анализа, я хочу перейти от общей картины к конкретному клиенту и увидеть его продуктовый контекст, чтобы изучить наполнение по выбранному НБС.**
- [ ] Я могу найти или выбрать конкретный узел и увидеть его расположение в графе.
- [ ] Выбранный узел визуально выделен.
- [ ] Клиент и продукт, наличие выбранного НБС и сегмент различимы; значение цветов объясняется легендой.
- [ ] Я могу перемещаться по схеме и менять масштаб, сохраняя возможность рассматривать выбранный объект и его связи.
- [ ] Граф остаётся читаемым при увеличении числа отображаемых объектов.
- Notes: Встреча исключила из выбранного сценария иерархию владения, дочерние и внучатые компании. Поиск и проверка нового клиента также не входят в него.

### [EPIC-005] Собрать основания для решения менеджера

---
**[US-005][Пользователь анализа] Как пользователь анализа, я хочу сравнить клиентов с выбранным НБС с похожими клиентами без него, чтобы найти возможные предложения для текущего портфеля.**
- [ ] Я вижу общие характеристики клиентов, у которых уже есть выбранный продукт.
- [ ] Я вижу клиентов без продукта и факты, которые могут быть полезны при рассмотрении продукта; похожесть не считается доказательством пригодности.
- [ ] Подсказка показывает факты, источники и интерпретацию отдельно.
- [ ] Если фактов недостаточно или они противоречат друг другу, это явно указано.
- Notes: В ТЗ численность сотрудников, регион, сегмент и вид деятельности приведены как возможные признаки. В рабочем baseline они не превращаются в правила пригодности.
---
**[US-006][Пользователь анализа] Как пользователь анализа, я хочу видеть рекомендацию по продукту для конкретного клиента и её обоснование, чтобы оценить, стоит ли рассматривать предложение.**
- [ ] Рекомендация сформулирована как предложение для рассмотрения, а не как безусловный вывод о клиенте.
- [ ] Я могу проследить цепочку «источник → факт → почему стоит рассмотреть → что нужно проверить».
- [ ] Обоснование учитывает доступные сведения о сфере деятельности, ВЭД, продуктах конкурентов и продуктовых критериях.
- [ ] Если по клиенту есть исключающий фактор, рекомендация не представляется как подходящая.
- [ ] Если сведений недостаточно, пользователь видит это ограничение.
- Notes: Нулевая выручка, банкротство и несуществующее юридическое лицо названы в ТЗ как возможные исключения; их наличие должно быть подтверждено источником. Для ДМС ориентир «сотрудники → ДМС» не является формальным правилом. Подсказка возможна без матрицы, если есть проверяемые сведения; при их отсутствии система воздерживается от содержательного вывода.
---
**[SS-002][Система] Как система, я хочу отделять наблюдаемое состояние продукта от подсказки и отмечать пробелы, чтобы не выдавать отсутствие продукта за потенциал продажи.**
- [ ] Отдельно видны состояние продукта (есть, не обнаружен, ранее подключался, отключён, неизвестно) и состояние подсказки (есть основания рассмотреть, данных недостаточно, обнаружено предостережение).
- [ ] Подтверждённый исключающий фактор показан с источником и не скрывается за положительной формулировкой.
- [ ] Для каждого существенного факта указаны источник, дата и привязка к клиенту; неизвестное не считается отрицательным фактом.
- [ ] Система не представляет подсказку как проверенную применимость или окончательное решение.
- Notes: Формальной матрицы нет; ориентиры из пересланной таблицы помогают сформулировать вопрос для менеджера, но не являются правилами пригодности.
---
**[SS-003][Система] Как система, я хочу собрать карточку оснований для менеджера, чтобы сократить ручной поиск по источникам.**
- [ ] Карточка содержит формулировку «стоит рассмотреть, потому что…», подтверждающие факты и ссылки на исходные записи.
- [ ] Карточка содержит недостающие и противоречивые сведения, а также дату каждого источника.
- [ ] Если источник не связан с конкретным клиентом достаточно надёжно, факт не используется в персональной подсказке.
- [ ] Карточка не содержит вероятности покупки или статуса «продукт подходит».
- Notes: Это рабочая замена исходному требованию о предиктивном NBO. Её нужно оценивать по достоверности сборки фактов и времени менеджера; синтетика позволяет проверить только сценарий.
---
**[US-007][Пользователь анализа] Как пользователь анализа, я хочу отметить, что сделал с рекомендацией, и указать причину, чтобы зафиксировать её релевантность для текущей работы.**
- [ ] Я могу отметить рекомендацию как принятую, отложенную или нерелевантную.
- [ ] Для отметки я могу указать причину.
- [ ] Отметка относится к конкретной рекомендации и клиенту.
- Notes: Пользователь подтвердил включение обратной связи и причины в MVP. В карте не предполагается, что эти отметки автоматически переобучают или меняют рекомендации.

- [ ] Даты сравниваемых срезов видны пользователю.

## Gap Analysis & Risks

### Пропущенные функции

- Не выявлены дополнительные независимые сценарии для выбранного MVP. Встреча сузила проект до одного сценария по НБС. Сбор обратной связи по рекомендациям включён по более раннему решению пользователя.
- Внешний ориентир: материалы Microsoft по рекомендованным действиям также описывают приоритизацию, показ причин и обратную связь о релевантности: [Recommended actions overview](https://learn.microsoft.com/en-us/dynamics365/sales/recommended-actions-overview), [Manage risks and prioritize actions based on AI recommendations](https://learn.microsoft.com/en-us/dynamics365/sales/next-best-actions-to-manage-opportunities), [Responsible AI FAQ](https://learn.microsoft.com/en-us/dynamics365/sales/faqs-about-recommended-actions-agent-responsible-ai).

### Закрытые решения по границам MVP

- Экспорт графа и аналитического отчёта — обязательный финальный шаг сквозного сценария. Для графа указаны PNG/SVG/PDF/PPTX, для отчёта — PDF/PPTX.
- Сценарий заканчивается рекомендацией и экспортированным аналитическим результатом. Граф не ведёт статусы продажи и не фиксирует оплату договора; это остаётся бизнес-результатом за пределами MVP.
- Для демонстрации команда полностью генерирует клиентские данные: заказчик подтвердил, что не передаст исходные записи. На встрече он принял, что синтетические зависимости и рекомендации не представляют реальный портфель и нужны для демонстрации pipeline без заявления о качестве. Объём около 500 тысяч записей был назван как примерный масштаб клиентского источника; размер синтетического эталона не утверждён, а предложенные командой 100 тысяч наборов не согласованы.
- Для демонстрации используются два отдельных режима: синтетический портфель и точечные публичные факты о реальных организациях из ФНС и разрешённых страниц компаний. Реальные факты не прикрепляются к синтетическим клиентам. СПАРК без договора исключён; см. [MVP baseline](./mvp-baseline.md).
- На встрече заказчик подтвердил желаемое пополнение/автообновление перечня НБС при обновлении витрины. Интеграция, доступ к витрине и включение автоматического обновления в MVP не решены.
- В сценарий не входят новые клиенты и структура владения дочерними/внучатыми компаниями.
- Бизнес-группы пользователя — развитие НБС, бизнес и ДЗО. Прикладные роли — администратор (редактирование данных) и пользователь анализа. Для локального MVP отдельный вход не предусмотрен; точная матрица прав и способ демонстрации ролей без входа не определены. Будущая банковская аутентификация согласуется отдельно с ИБ.
- Оценка заказчика «около 500 тысяч клиентов» относится к масштабу источника. Предложение команды о 100 тысячах синтетических наборов параметров не утверждено и не является критерием MVP.
- Подсказка к рассмотрению может формироваться без формальных критериев при наличии проверяемых фактов. Ориентиры не превращаются в автоматические правила пригодности; если факт нельзя связать с клиентом, система показывает пробел и воздерживается от вывода.
- В MVP пользователь может отметить рекомендацию как принятую, отложенную или нерелевантную и указать причину. Автоматическое обучение на такой обратной связи не подразумевается.
- Отдельный Release 1.1 не планируется; его возможное появление не входит в текущую карту.

### Отложено по решению пользователя

- **Открытые источники:** для отдельного режима открытых фактов выбраны точечные сведения ФНС и разрешённые страницы компаний; конкретные URL фиксируются с датами. СПАРК исключён из открытого baseline без договорного доступа. См. [MVP baseline](./mvp-baseline.md).
- **Автообновление каталога НБС:** заказчик хочет дополнять неполный перечень и автоматически обновлять данные при изменении витрины, но неизвестны витрина, механизм, периодичность и объём MVP-интеграции.
- **Размер синтетического набора:** около 500 тысяч записей — оценка клиентского источника; 100 тысяч наборов параметров были предложены командой без подтверждения заказчика. Целевой объём для демонстрации открыт.
- **Роли и права:** нужно определить список изменяемых данных для администратора, полномочия пользователя анализа и способ демонстрации/проверки роли без отдельного входа в локальном MVP. Аутентификацию для будущего банковского использования согласовать с ИБ.
- **Нумерация сценария:** в стенограмме прозвучали номера 11 и 2; по содержанию понятно, что оставлен сценарий наполненности по НБС. Номер можно сверить с каталогом исходных сценариев, если он понадобится в отчётности.

### Риски

- [⚠️ Risk] Отсутствие продукта не означает потенциал продажи. Неправильная привязка источника или интерпретация ориентира как правила может ввести менеджера в заблуждение.
- [⚠️ Risk] Оплата договора остаётся бизнес-результатом вне графа. Экспорт рекомендаций и аналитики не означает, что предложение было принято или договор оплачен.
- [⚠️ Risk] Конкретный открытый источник и дата его сведений отложены; перед подготовкой демонстрационных данных понадобится выбрать источник, проверить условия использования и зафиксировать период.
- [⚠️ Risk] Для обработки файла нужно однозначное сопоставление клиента. ТЗ указывает ИНН + КПП + внутренний Client ID, но не описывает разбор конфликтов и дубликатов между источниками.
- [⚠️ Risk] Временное сравнение требует истории изменений; доступные даты и полнота тестовых данных пока не определены.
- [⚠️ Risk] Синтетические данные позволяют показать интерфейс и сборку фактов, но не подтверждают экономию времени или полезность подсказки в реальной работе.
- [⚠️ Risk] Если размер демонстрационного набора будет существенно меньше ориентировочных 500 тысяч клиентских записей источника, результаты проверки скорости не будут представлять этот объём.

### Уровень неопределённости USM

**Предварительная оценка заполненности структуры: 0,075.** Это не оценка достоверности требований и не вероятность того, что карта верна. Расчёт по бинарной формуле методики:

- Критические разделы заполнены: Backbone, эпики, пользовательские истории MVP и критерии приёмки — `0 / 4 × 0,7 = 0`.
- Из вспомогательных разделов состав следующего релиза и его отсутствие отражены как решение; детализация обновления открытых данных отложена, поэтому System Stories пока не закрывают этот вариант — `1 / 4 × 0,3 = 0,075`.
- Итого: `0 + 0,075 = 0,075`.

Это практический минимум при текущих материалах: конкретный источник и режим его обновления отложены, но основные истории и границы сценария зафиксированы по требованиям и ответам пользователя.
