# API Inventory: анализ наполненности НБС — ПСБ × ИТМО

> **Версия:** 0.1 — рабочий контракт для планирования  
> **Дата:** 2026-11-18  
> **Основано на:** `artifacts/usm.md` (итерация 1), `artifacts/er-diagram.md` (v0.3), `artifacts/c4-architecture.md` (v0.6), `artifacts/nfr.md`, `artifacts/brief.md`.  
> **Статус:** предложения по маршрутам и контрактам; не OpenAPI и не утверждённая спецификация.

> **Уточнение 20.11.2026:** ресурс `/recommendations` означает подсказку менеджеру к рассмотрению, а не проверенную применимость или прогноз покупки. Ответ должен сохранять использованные факты, источники и пробелы; исходный NBO из ТЗ в baseline не реализуется.

## Обзор

**Всего endpoints:** 26.  
**API Style:** REST, `/api/v1/`.  
**Форматы:** JSON по умолчанию; `multipart/form-data` для предварительного разбора файла; PDF/PPTX возвращаются как бинарные файлы с `Content-Disposition: attachment`.  
**Базовый URL — гипотеза:** `http://127.0.0.1:<API_PORT>/api/v1`; порт в C4 не задан.  
**Авторизация:** отдельного входа в локальном MVP нет. Auth endpoints не предлагаются. Локальный переключатель роли в UI скрывает действия записи в режиме анализа, но прямой вызов API этим не защищён. Для реального использования внутри Банка аутентификацию и права нужно отдельно согласовать с ИБ.

Предполагается синхронная обработка для локальной демонстрации. Если импорт, расчёт рекомендаций или экспорт не укладываются в запрос-ответ, потребуется асинхронный job API и Sequence diagram. Размеры файлов, пределы выдачи и временные ограничения пока не определены.

### Общие правила

- Идентификаторы ресурсов в URL — UUID из ER. Идентификаторы источника, ИНН и КПП передаются и хранятся как строки.
- Записи `Client ID` сопоставляются между срезами по основному ключу `source_client_id`. ИНН/КПП используются только для проверки и не переопределяют клиента.
- Фильтры и сортировка применяются на backend; API возвращает выбранный срез и нужные агрегаты, а не весь портфель.
- В списках рекомендуется единый формат `?page=1&limit=50` и ответ `pagination { page, limit, total }`. Значения по умолчанию/максимум нужно сверить с размером синтетического набора.
- Изменение профиля, состояния продукта или факта в сохранённом срезе создаёт новый срез с `parent_snapshot_id`; старый остаётся доступен. Ответ записи содержит новый `snapshot_id`, который UI выбирает для следующего действия.
- Удаление клиентов, срезов, рекомендаций и продуктов не включено: соответствующей истории нет, политика хранения не согласована.

### `POST /imports/preview`

**Request:** `multipart/form-data`: `file` (XLSX или CSV UTF-8; запятая/точка с запятой для CSV). Старый XLS не поддерживается.  
Файл содержит только синтетические клиентские и продуктовые поля, сведения о конкурентах/условиях и заметки сотрудника. Реальные организации готовятся в отдельном наборе и загружаются offline seed-процедурой, не через этот маршрут.  
**`200` response:** `preview_id`, `expires_at`, найденные колонки, предполагаемое сопоставление, счётчики и `issues[]` с номером строки, полем, кодом и пояснением. Preview хранится локально до commit либо 30 минут (предлагаемый технический TTL), затем удаляется вместе с временным файлом. Preview не записывает нормализованные сущности в постоянную БД.  
**Ошибки:** `400` нечитаемый файл/параметры; `413` файл больше установленного предела (предел пока не задан); `415` неподдерживаемый формат; `422` файл не соответствует ожидаемой структуре.

### `POST /snapshots`

**Request JSON:** `preview_id`, `snapshot_date`, подтверждённый `column_mapping`.  
**`201` response:** `snapshot_id`, `snapshot_date`, `import_status=loaded`, число принятых строк. При повторном идентичном запросе того же preview — `200` и тот же `snapshot_id`; отличающийся повторный запрос — `409`.  
**Ошибки:** `404` preview не найден; `410` preview истёк; `409` конфликт повторного запроса; `422` ошибки структуры, неоднозначные строки или повтор Client ID. При любой ошибке срез и дочерние записи не создаются. После исправления файла требуется новый preview. `Client ID` остаётся ключом синтетических срезов, а КПП в исходной XLSX-схеме нет.

## 4. Покрытие и карточка клиента

| Method | Path | Auth / роль | Description | User Story |
|---|---|---|---|---|
| GET | `/coverage/graph?snapshot_id={id}&product_id={id}` | Без входа | Фильтрованный подграф и агрегаты `present`, `absent`, `unknown`, `total` по выбранному НБС и группе; доля только по известным состояниям. | US-002, US-003, US-005 |
| GET | `/clients/{client_id}/profiles/{snapshot_id}` | Без входа | Профиль клиента на выбранную дату, его продуктовые состояния и связанный контекст/сведения. | US-004, US-006 |
| PATCH | `/client-profiles/{profile_id}` | Без входа; действие администратора в UI | Создать производный срез с изменённым профилем; вернуть новый `snapshot_id`. | US-012 |
| PUT | `/client-profiles/{profile_id}/products/{product_id}` | Без входа; действие администратора в UI | Создать производный срез с изменённым состоянием продукта; вернуть новый `snapshot_id`. | US-012 |
| PATCH | `/evidence-items/{evidence_id}` | Без входа; действие администратора в UI | Создать производный срез с исправленной заметкой; вернуть новый `snapshot_id`. | US-012 |

`GET /coverage/graph` возвращает узлы, связи, легенду/типы и агрегаты только для выбранного синтетического среза. В каждой группе `total = present + absent + unknown`; `observed_share = present / (present + absent)` или `null` при нулевом знаменателе. Доля описывает только наблюдаемое покрытие при заданных фильтрах, не спрос или потенциал. Возвращать `known_count` и `unknown_count` вместе с ней; не присваивать группам оценку «хорошо/плохо» или рейтинг продажи. `GET` профиля может включать только синтетические сведения соответствующего клиента; реальные публичные факты читаются отдельным маршрутом.

Для всех трёх операций изменения backend копирует исходный срез и связанные с ним данные, применяет правку в одной транзакции и создаёт новый `data_snapshots.id` с `parent_snapshot_id` исходного среза. Запуски и карточки на старом срезе сохраняются; новые строятся по новой версии. Отдельное изменение записи каталога `products` не должно ретроспективно менять название в историческом выводе: перед реализацией истории каталога нужны сохранённые отображаемые значения или версионирование записи. Политика удаления не задана.

## 5. Рекомендации и обратная связь

| Method | Path | Auth / роль | Description | User Story |
|---|---|---|---|---|
| POST | `/recommendation-runs` | Без входа | Запуск pipeline для среза, целевого НБС и набора фильтров. | US-005, US-006, SS-002, SS-003 |
| GET | `/recommendation-runs/{run_id}` | Без входа | Сводка запуска, версия сборки фактов, статус и число карточек. | US-005, SS-003 |
| GET | `/recommendations?run_id={id}&status={status}` | Без входа | Страница подсказок с фильтром по `review_status`; порядок по полноте свидетельств допустим только с ясной подписью. | US-005, SS-003 |
| GET | `/recommendations/{recommendation_id}` | Без входа | Карточка клиента: `review_status`, «стоит рассмотреть», факты с `evidence_id`/источником/датой, предостережения и `information_gaps`; без score покупки. В синтетическом режиме может содержать отдельный экспериментальный `ml_candidate_status`. | US-006, SS-002 |
| POST | `/recommendations/{recommendation_id}/feedback` | Без входа; пользователь анализа по сценарию | Сохранить `accepted`, `deferred` или `irrelevant` и обязательную причину. | US-007 |

### `POST /recommendation-runs`

**Request JSON:** `snapshot_id`, `product_id` (должен быть НБС), согласованные фильтры.  
**Предлагаемый синхронный `201` response:** `run_id`, `snapshot_id`, `product_id`, `run_status`, `pipeline_version`, число карточек и сводные статусы. Результаты постранично читаются через `GET /recommendations`.
**Экспериментальный классификатор:** при включении offline обученной модели запуск сохраняет `model_version`, а карточка возвращает `ml_candidate_status` отдельно от базового `review_status` и использованных фактов. Без модели и для публичных компаний оба модельных поля равны `null`. Версия отсылает к воспроизводимому манифесту обучения; API обучения в пользовательском сценарии нет. Расхождение двух статусов показывается, а не скрывается.
**Поведение без правил:** наличие проверяемых фактов позволяет статус `consider` с источниками и пробелами. Без надёжно привязанных фактов возвращается `insufficient_data`; обнаруженные предостережения отражаются как `caution`. Поля вероятности покупки и `eligible` отсутствуют.
**Ошибки:** `404` срез или НБС не найден; `422` тип продукта неверный, фильтр недопустим или срез несовместим с запуском.

### `POST /recommendations/{recommendation_id}/feedback`

**Request JSON:** `{ "status": "accepted|deferred|irrelevant", "reason": "..." }`.  
**Предлагаемый `201` response:** созданная отметка и время.  
**Ошибки:** `404` рекомендация не найдена; `422` неизвестный статус или пустая причина. Идентификатор пользователя не сохраняется: входа в локальном MVP нет, автоматического переобучения на feedback не предусмотрено.

| Method | Path | Auth / роль | Description | User Story |
|---|---|---|---|---|
| GET | `/reports/analysis?run_id={id}` | Без входа | Данные/предпросмотр аналитического отчёта по запуску для отображения в интерфейсе. | US-010 |

Клиентская операция должна поддержать PNG/SVG/PDF/PPTX и выбрать поля/состояние, видимые пользователю. Если решение изменится и граф будет формировать backend, добавить `POST /exports/graph`.

## Маппинг ER → API

| ER-ресурс | API-покрытие |
|---|---|
| `clients`, `client_snapshot_profiles`, `client_product_states` | `GET /clients/.../profiles/...`, `PATCH /client-profiles/...`, `PUT /client-profiles/.../products/...`; часть создаётся импортом. |
| `products`, `dzos`, `product_snapshot_states` | `GET/POST/PATCH /products`; ДЗО вложено в продукт, статус на дату приходит с `snapshot_id`; состояния создаются импортом. |
| `data_snapshots` | `POST/GET /snapshots`; срез создаётся из подтверждённого импорта. |
| `public_organizations`, `public_evidence_items` | `GET /public-organizations` и `GET /public-organizations/{id}`; записи создаёт отдельная offline seed-процедура. |
| `data_sources`, `source_observations`, `evidence_items` | Создаются при импорте/добавлении контекста; provenance возвращается с профилем, текст заметки можно поправить через `PATCH /evidence-items/{id}`. Отдельный CRUD каталога источников не нужен до выбора источника. |
| `applicability_rule_sets`, `applicability_criteria` | Читаются через `GET /products/{id}/applicability`; загрузка правил в UI/API не проектируется, пока критерии и процесс утверждения не определены. |
| `recommendation_runs`, `recommendation_run_rule_sets`, `recommendations`, `recommendation_feedback` | `POST/GET /recommendation-runs`, `GET /recommendations`, `POST /recommendations/{id}/feedback`. |
| `product_bundles`, `product_bundle_items` | `POST /product-bundles/analysis`, `GET /product-bundles`. |

## Приложения

### Коды ошибок

| HTTP | Code | Описание |
|---:|---|---|
| 400 | `INVALID_REQUEST` | Некорректный JSON или query parameters. |
| 401 | `UNAUTHORIZED` | Не используется в локальном MVP; зарезервирован для будущего auth-профиля. |
| 403 | `FORBIDDEN` | Не используется в локальном MVP; переключатель роли в UI не защищает API. |
| 410 | `PREVIEW_EXPIRED` | Временный предпросмотр истёк, нужен новый разбор файла. |
| 404 | `NOT_FOUND` | Срез, клиент, продукт, рекомендация или preview не найдены. |
| 409 | `CONFLICT` | Дубли Client ID в одном импорте, повторное подтверждение preview или конфликт каталога. |
| 413 | `PAYLOAD_TOO_LARGE` | Файл превышает лимит; лимит нужно установить. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Формат не поддерживается (например, старый XLS). |
| 422 | `VALIDATION_ERROR` | Поля, идентификаторы, фильтры или бизнес-условия невалидны. |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка сервера; не включать содержимое файла/заметок в технический ответ без решения ИБ. |

### Формат ошибки — предложение

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Часть строк не прошла проверку",
    "details": [
      {
        "row": 12,
        "field": "inn",
        "issue": "INVALID_FORMAT"
      }
    ]
  }
}
```

### Пагинация — предложение

`?page=1&limit=50` для каталогов, профилей и списков рекомендаций. Ответ: `{ "items": [], "pagination": { "page": 1, "limit": 50, "total": 0 } }`. Пределы `limit`, объём preview/issues и способ постраничного получения подграфа требуют проверки на целевом моковом наборе.

## Открытые решения перед реализацией

1. Как назначать демонстрационные роли администратора/аналитика без отдельного входа и как API должен различать запись/чтение.
2. Импорт атомарный или частичный; какие ошибки блокируют commit, какие строки оператор может исключить, сколько живёт preview.
3. Редактирование и неизменность срезов: можно ли править профиль/состояние после запуска анализа или исправление должно создавать новый срез.
4. Лимит файла, число выдаваемых nodes/edges, `limit`/timeout и синхронность импорта, сборки карточек, анализа bundles и экспорта.
5. Набор фактов и источников для контрольного кейса ДМС, надёжность привязки к клиенту и допустимые поля проверки ИНН/КПП. Подсказка возможна без формальных критериев, но не означает пригодность продукта.
6. Этап расчёта продуктовых связок: по запросу или при импорте; формула частоты/уверенности и источник условий/скидок.
7. Для точечных открытых фактов выбраны ФНС и разрешённые страницы компаний; решить, достаточно ли общего импорта подготовленных фрагментов или нужен отдельный маршрут. API для live внешних систем не включён.
8. Graph export остаётся клиентским по C4-гипотезе; проверить реализацию форматов PNG/SVG/PDF/PPTX после выбора библиотеки.
