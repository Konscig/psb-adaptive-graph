# Нефункциональные требования (NFR)

> Проект: Универсальный адаптивный граф связей для ПСБ × ИТМО  
> Дата: 2026-11-18  
> Домен: внутреннее банковское аналитическое ПО; семестровый MVP/локальный прототип  
> Статус: рабочая версия после встречи с заказчиком 18.11.2026; оставшиеся неизвестные указаны отдельно. Значения со статусом «предложение» не являются требованиями заказчика.

## 1. Производительность (Performance Efficiency)

### 1.1 Профиль нагрузки

- **DAU:** только участники согласованных демонстраций; их число не задано.
- **MAU:** не задано.
- **Одновременные сессии (пик):** отдельный предел не задан; целевой профиль — текущий демонстрационный сценарий.
- **Масштаб источника:** на встрече заказчик оценил клиентскую часть примерно в 500 тысяч записей. Это ориентир из устной оценки, а не согласованный предел или требование обработать весь объём в MVP.
- **Размер тестового графа и эталонного набора:** заказчик не предоставляет данные; команда должна подготовить синтетический набор минимум с двумя периодами. На встрече команда упомянула 100 тысяч наборов параметров, но заказчик не утвердил это число. Число узлов и связей фиксируется после выбора объёма синтетики.
- **Размер входного файла:** задаётся после генерации эталонного синтетического набора.

### 1.2 Пропускная способность (Throughput)

- **Средняя и пиковая нагрузка:** не задана.
- **RPS:** не задано. В материалах не определены границы запросов и нагрузочный профиль; значение нельзя вывести из числа пользователей или объёма графа.
- Критичные пользовательские действия для будущего замера: открыть граф, изменить фильтры, сравнить периоды, получить рекомендации, подготовить и экспортировать отчёт.

### 1.3 Время отклика (Latency)

- **Появление страницы (LCP):** ≤ 2,5 с на 75-м процентиле — принято пользователем как ориентир для появления страницы.
- **Полная готовность графа к взаимодействию:** целевое время не задано и должно измеряться отдельно от появления первого содержимого.
- **Применение фильтра, сравнение периодов, расчёт рекомендаций и экспорт:** целевое время не задано.
- **Критерий «понять структуру схемы за 10–15 секунд»** есть в ТЗ, но это критерий понятности, а не скорости загрузки.
- [Справочный ориентир, не требование MVP] Остальные Core Web Vitals — INP ≤ 200 мс и CLS ≤ 0,1 на 75-м процентиле. [Источник: web.dev — Core Web Vitals](https://web.dev/articles/vitals).
- Для выбора целевого времени надо измерять на согласованном тестовом наборе с фиксированными размерами файла, числом узлов и связей.

- **Плановое окно обслуживания:** не задано.
- Критерий для MVP проверяется на согласованных демонстрациях. Процент годовой доступности не устанавливается.

### 2.2 Целостность данных (RPO — Recovery Point Objective)

- **Максимально допустимая потеря данных:** не задана.
- Не определено, какие результаты должны переживать сбой: исходный тестовый файл, состояние графа, отметки пользователя о рекомендациях, сгенерированные отчёты или всё перечисленное.

### 2.3 Скорость восстановления (RTO — Recovery Time Objective)

- **Время восстановления:** не задано.
- Не определено, может ли MVP после сбоя быть восстановлен повторной загрузкой подготовленных данных или требуется восстановить последнее состояние работы.
- Для обсуждения RTO/RPO использована методика планирования восстановления NIST SP 800-34; это ориентир, не требование ПСБ и не российский отраслевой норматив. [Источник: NIST SP 800-34 Rev. 1](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final).

## 3. Безопасность (Security)

### 3.1 Регуляторные требования (Compliance)

- [ ] **152-ФЗ:** применимость для MVP не подтверждена. Команда проекта использует подготовленные/синтетические данные и не работает с реальными конфиденциальными клиентскими данными. Для будущего банковского использования банк должен определить, обрабатываются ли персональные данные и какие требования к их защите действуют.
- [ ] **PCI DSS:** не выявлен в текущем объёме: граф не принимает и не обрабатывает данные платёжных карт. Пересмотреть, если такой тип данных или операция появятся.
- [ ] **GDPR:** применимость не установлена; в проектных материалах нет подтверждённого сценария обработки данных субъектов ЕС.
- [ ] **Внутренние стандарты СБ ПСБ:** финальные требования ИБ в материалах отмечены как требующие отдельного согласования.
- [ ] **Другое:** не задано.
- [💡 Предложение] Если прототип будет веб-приложением, использовать OWASP ASVS 5.0 как контрольный перечень для последующей проверки безопасности. Это ориентир для анализа, а не утверждение о соответствии стандарту. [Источник: OWASP ASVS](https://asvs.owasp.org/).

### 3.2 Классификация данных

- **Для локального MVP:** заказчик не предоставляет данные; команда готовит полностью синтетический набор по `artifacts/schema.xlsx`. Он не должен копировать данные реальных компаний или содержать реальные клиентские записи. Реальные конфиденциальные сведения студентам не передаются.
- **Для дальнейшего развития:** банковские данные не должны выходить за периметр Банка.
- **Класс/категория банковских данных и уровень защищённости:** не определены; их должен подтвердить владелец данных и подразделение ИБ.
- В синтетическом наборе могут быть поля ИНН, продукты, конкуренты и заметки. Тестовые идентификаторы не должны сопоставляться с реальными реестрами или компаниями. Имена физических лиц и контакты в демо-набор не включаются.
- Применимость требований 152-ФЗ зависит от фактического состава и обработки данных; документ не устанавливает юридическую классификацию. [Источник: статья 19 152-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61801/ca9e5658710519f09ab2fdb8196fcb3eb024a051/).

### 3.3 Аутентификация и авторизация

- **Роли MVP:** на встрече заказчик назвал администратора, который может редактировать данные, и пользователя анализа. Подробная матрица разрешений не задана.
- **Аутентификация:** для локального MVP подтверждён запуск без отдельного входа. Встреча добавила прикладные роли, но способ демонстрации их разных действий без входа не выбран. Это открытый вопрос интерфейса/режима демо, а не требование добавить аутентификацию в MVP.
- **Будущий банковский доступ:** требования к аутентификации и разделению доступа по ролям должны быть согласованы с ИБ до использования внутри Банка. Сотрудники развития НБС, бизнес и ДЗО остаются бизнес-группами пользователей; их соответствие ролям администратора/пользователя не задано.
- **Парольная политика, срок сессии и автоматическое завершение сессии:** не заданы.
- Доступ для будущего использования внутри банковской платформы требует согласования с ИБ; способ входа не выбирается этим документом.

### 3.4 Локализация данных

- **Подтверждённое ограничение:** банковские данные должны оставаться внутри периметра Банка.
- **Географическое место хранения, трансграничная передача и обработка открытых источников:** не определены отдельно. «Внутри периметра» не трактуется здесь как автоматически согласованное место хранения.
- Для MVP студенческая команда использует только подготовленные/синтетические данные.

## 4. Масштабируемость (Scalability)

### 4.1 Ожидаемый рост

- **Через 6 месяцев:** число пользователей и объём данных не заданы.
- **Через 1 год:** не заданы; отдельный релиз после MVP, по словам пользователя, не согласован и, скорее всего, не планируется.
- **Через 3 года:** не задано; горизонт промышленного развития в текущих материалах не определён.
- Базовый профиль MVP ограничен текущим моковым набором; максимальное количество клиентов, узлов, связей и исторических срезов численно не задано. На встрече заказчик назвал приблизительный масштаб клиентского источника — около 500 тысяч записей, но это не утверждённый объём демонстрации.

### 4.2 Требования к масштабированию

- **Горизонтальное масштабирование:** не задано; документ не выбирает архитектуру.
- **Пределы пользователей, операций и данных:** не заданы. На встрече назван приблизительный масштаб источника — около 500 тысяч клиентов; размер набора для MVP не согласован.
- **Подтверждённое качественное требование:** граф не должен терять читаемость при увеличении числа объектов. В сценарии показывается выбранный срез, а не вся база клиентов. Для измеримой приёмки нужно закрепить количество записей, узлов и связей в моковом наборе и критерий читаемости.

## 7. Совместимость (Compatibility)

### 7.1 Клиентские устройства

- **Режим интерфейса для MVP:** настольный браузер; поддерживаются актуальные версии Chrome и Edge на дату демонстрации. Минимальная ширина окна — 1280 px как рабочий ориентир; мобильные устройства и планшеты в текущий объём не входят.
- **Запуск демо:** пользователь подтвердил Docker на одной машине. ОС хоста пока не выбрана; Docker Compose — гипотеза C4 для совместного запуска веб-приложения, API, локального ML runtime и PostgreSQL.
- **Входные файлы:** `.xlsx` и `.csv` в UTF-8; CSV с разделителем-запятой или точкой с запятой. Старый формат `.xls` в MVP не поддерживается.
- **Экспорт графа:** PNG, SVG, PDF или PPTX; **отчёта:** PDF или PPTX — по ТЗ и подтверждённому сценарию.
- Заказчик попросил перед экспортом настраивать поля и сохранять в файле представление, которое отображается на экране. Форматы и воспроизведение отображаемого состояния нужно проверить на выбранной библиотеке визуализации. Упоминание формата страницы «A4» в стенограмме распознано неуверенно и не включено как требование.

### 7.2 Сеть

- **Сетевой профиль демо:** один компьютер; baseline предполагает локальное соединение браузера с API через loopback. Доступ с других устройств в текущем профиле не предусмотрен.
- **AI runtime:** предпочтён локальный запуск модели на демонстрационной машине; внешний model API в baseline не планируется. Генерация/embeddings нужны только если команда подтвердит RAG.
- **Интернет/VPN/офлайн-режим:** после загрузки приложения, моделей, синтетического набора и подготовленного файла открытого контекста демо может работать без внешнего соединения. Пользователь подтвердил открытые данные для демонстрации, но способ получения конкретного источника остаётся неуточнённым.
- **Будущее банковское использование:** решение должно работать внутри банковской платформы и не выводить данные Банка за периметр.
- На встрече заказчик предложил рассмотреть СПАРК, сайт клиента и налоговую службу. Источник не выбран; доступность, ограничения использования и режим обновления нужно проверить. Конкретная интеграция в MVP не подтверждена.

### 7.3 Интеграции и заданная среда

- В ТЗ стейкхолдера указаны данные в Hadoop, выделенная виртуальная машина с Python 3.10 и доступ пользователей к данным через банковскую платформу.
- Эти параметры зафиксированы как сведения из ТЗ, а не как рекомендации по архитектуре. Ограничения ИБ и возможность их применения должны быть подтверждены профильной командой Банка.
- Полная интеграция со всеми банковскими системами не является результатом семестрового проекта. На встрече заказчик отметил, что каталог НБС неполный, и выразил ожидание его дополнения/обновления при изменении витрины. Доступ и механизм интеграции не определены; это цель дальнейшей проработки, а не готовая функция MVP.
- Протоколы, интерфейсы интеграции и внешние системы для MVP не согласованы.
- **Архитектурная гипотеза C4:** контейнеры запускаются через Docker на одной машине; Docker Compose и локальный ML runtime — гипотезы. PostgreSQL предлагается как основная база, pgvector — только если команда подтвердит RAG. RAG по документам компании остаётся гипотезой пользователя; модели и форматы документов сверх XLSX/CSV не зафиксированы как требования ТЗ.

Заказчик назвал приблизительный объём около 500 тысяч клиентских записей в источнике, но размер мокового эталона и производственная цель не согласованы.
- Проект одновременно описан как локальный семестровый прототип и как основа для последующего использования внутри банковской платформы. Их требования к безопасности, доступности и сопровождению различаются; в этой версии они разделены.
- Для локального MVP подтверждены синтетический набор и запуск без отдельного входа. На встрече заказчик выделил администратора и пользователя анализа; точные права и способ демонстрации различий действий без входа остаются открытыми.
- ТЗ фиксирует запрет вывода банковских данных за периметр, но не задаёт классификацию данных и сроки хранения.
- Требование понятности схемы за 10–15 секунд относится к удобству понимания, а не к времени загрузки.

### Серые зоны

- Число участников демонстраций и размер синтетического файла, который команда ещё должна подготовить. Оценка заказчика примерно в 500 тысяч клиентов и предложенные командой 100 тысяч синтетических наборов не образуют согласованный нагрузочный профиль.
- Допустимое время полной готовности графа, фильтрации, сравнения, рекомендаций и экспорта; для LCP уже принят ориентир 2,5 секунды на 75-м процентиле.
- Объём допустимой потери результатов и время восстановления после сбоя.
- Будет ли в любом тестовом наборе информация, относящаяся к физическим лицам; классификация данных и обязательные меры ИБ.
- Точная матрица прав администратора и пользователя анализа, способ демонстрации их различий без входа и необходимость журнала действий.
- ОС демонстрационной машины, ресурсы локального NBO runtime и необходимость интернета при получении выбранных открытых данных. RAG по документам остаётся гипотезой. Браузеры Chrome/Edge, desktop-режим и локальное соединение приложения уже зафиксированы для демо.
- Какую витрину использовать для дополнения каталога НБС, как часто она обновляется и входит ли автоматическая синхронизация в семестровый MVP.
- Срок хранения, удаление, архивирование и резервное копирование файлов, отчётов, рекомендаций, отметок обратной связи и журналов.
- Владелец поддержки после окончания семестра и ожидаемая частота обновлений.
- Для демо согласован показ локального скоринга и ранжирования NBO на моковых данных без заявления о качестве. Количественная оценка остаётся открытой до появления размеченной выборки и согласованной метрики.

### Рекомендации

- Разделить критерии приёмки локального MVP и будущего банковского развёртывания; не переносить целевые значения производственной системы на демонстрационный прототип без решения заказчика.
- До нагрузочной приёмки зафиксировать один референсный тестовый набор: объём файла, количество компаний/узлов/связей и число одновременно работающих пользователей.
- Перед работой с любыми данными Банка получить от ИБ классификацию данных, требования к входу, ролям, журналированию, хранению и размещению.
- Утвердить RTO/RPO через сценарий последствий: что именно пользователь потеряет при сбое и как долго может ждать восстановления.
- Использовать ISO/IEC 25010:2023 как таксономию качества продукта, OWASP ASVS 5.0 как возможный ориентир для оценки безопасности веб-приложения, а NIST SP 800-34 Rev. 1 — как вспомогательное руководство по планированию восстановления. Это ориентиры, не подтверждённые требования ПСБ: [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html), [OWASP ASVS 5.0](https://asvs.owasp.org/), [NIST SP 800-34 Rev. 1](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final).

### Уровень неопределённости NFR

**[Уровень неопределённости: 0,65]** по формуле методики после ответов пользователя и встречи 18.11.2026:

- Критические разделы без достаточных измеримых целей: надёжность (доступность на демонстрациях определена, RPO/RTO нет) и масштабируемость (профиль ограничен моковым набором, но его размер не зафиксирован) — `2 / 4 × 0,7 = 0,35`.
- Вспомогательные разделы пока заполнены только частично: сопровождение, наблюдаемость, совместимость, жизненный цикл данных — `4 / 4 × 0,3 = 0,30`.
- Итог: `0,35 + 0,30 = 0,65`.

Оценка отражает заполненность разделов NFR, а не качество продукта и не вероятность успешной реализации. Для безопасности зафиксирована граница локального MVP; требования банковской эксплуатации остаются за пределами этого профиля.
